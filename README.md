# Эпик: Реестр ассистентов и запуск flow

**Сервис:** `assistant-service` (новый)
**Статус:** draft, до груминга
**Оценка:** 13 SP / ~40 ч (шкала: 1 SP ≈ 3 ч)

---

## 1. Проблема

Langflow в платформе стоит, Wizard встроен, flow пользователи создавать умеют. Но платформа про эти flow ничего не знает — нет связи между flow в Langflow и проектом в Mosaix.

Отсюда две проблемы. Нельзя сказать, чей это flow: Langflow один на всех, тенантов не различает. И запустить flow можно только напрямую в Langflow, то есть мимо прав, мимо аудита, мимо лимитов.

## 2. Что сделать

1. Завести сервис `assistant-service` — FastAPI, PostgreSQL, SQLAlchemy, миграции.
2. Спроектировать реестр: ассистент = `flow_id` + название + владелец + проект.
3. Сделать три эндпоинта: регистрация, список, запуск.
4. Закрыть мультитенантность: личность и проект берём только из заголовков от nginx, из тела запроса — никогда. Чужой ассистент недоступен ни на чтение, ни на запуск.
5. Написать клиент к Langflow: таймауты, ретраи, разбор вложенного `outputs`, внятная ошибка вместо 500, когда Langflow лёг или ответил мусором.
6. Писать журнал запусков — кто, что, когда, сколько заняло, чем кончилось.
7. Покрыть тестами, включая негативные сценарии по Langflow.
8. Собрать docker-compose, конфиг, README.

**Не делаем:** редактирование и версионирование самих flow (это Wizard), асинхронный запуск и стриминг, продолжение диалога по `session_id`, квоты и rate-limit, биллинг по токенам, шаринг ассистентов между проектами.

## 3. DoD

1. Три эндпоинта работают по контракту из ТЗ.
2. Ассистент чужого проекта отдаёт 404 — не 403, существование чужих объектов не подтверждаем.
3. Ошибки Langflow не превращаются в 500: битый flow → 424, недоступность → 502, таймаут → 504.
4. Каждый запуск попадает в журнал, включая неудачный.
5. Есть тесты, зелёный CI.
6. `docker compose up` поднимает сервис с чистой базой, миграции применяются сами.
7. README: как запустить, как прогнать тесты, какие переменные окружения нужны.
8. Код прошёл ревью, выкачен на stage, дым-тест пройден.

## 5. Задачи

Тесты пишутся внутри каждого этапа, отдельной задачи «покрыть тестами» нет.

### 1. Каркас проекта — 2 SP

Поднять пустой сервис, на который можно коммитить. FastAPI, структура слоёв, конфиг через env, Dockerfile и compose с PostgreSQL, линтеры и форматтер, pre-commit, pipeline в CI, `/health`. Первый тест, который гоняется в CI и падает, если что-то сломали.

### 2. Модель данных и миграции — 2 SP

Спроектировать реестр и завести схему. Таблицы `assistants` и `assistant_runs`, связь с проектом и пользователем, уникальность flow в рамках проекта, индексы под выборку по проекту, soft-delete. Alembic, миграции применяются автоматом на старте. Тесты на миграции вверх-вниз и на констрейнты.

### 3. Бизнес-логика реестра — 3 SP

Регистрация и список ассистентов. Схемы запроса и ответа, валидация, пагинация. Слой прав: личность и проект берём из заголовков nginx, из тела — никогда. Чужой ассистент отдаёт 404. Тесты на изоляцию тенанта — главное, что тут проверяется.

### 4. Коннектор к Langflow — 3 SP

Запуск ассистента. Async-клиент, таймауты, ретраи с backoff, разбор вложенного `outputs`, маппинг ошибок Langflow в коды платформы вместо голого 500. Эндпоинт запуска поверх клиента. Тесты на замоканном Langflow: успех, битый flow, недоступность, таймаут, ответ неожиданной формы.

### 5. Журнал запусков — 2 SP

Писать каждый запуск, включая упавший: кто, что, когда, сколько заняло, чем кончилось. Запись не должна ронять сам запуск, если база недоступна. Тесты на то, что неудачный запуск тоже попадает в журнал.

### 6. Метрики и observability — 1 SP

Структурные логи со сквозным `request_id`, метрики latency и error rate по запускам, дашборд-минимум. Делается последним, когда поведение сервиса уже устоялось.
